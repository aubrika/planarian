# Deviations

Where the implementation departs from `docs/SPEC.md`: SHOULD-level choices made differently (§5 preamble) and places where NixOS and the spec disagree on mechanism (§18.7). One entry per deviation.

| Date | Spec § | Deviation | Reason |
| --- | --- | --- | --- |
| 2026-10-26 | §15 | A catalog case whose VM fixture can't be made reliable (S3 suspend, mac80211_hwsim, greeter automation, withheld D-Bus replies) may run on `harness = ["fake"]` only. Each such move gets its own row here. | Owner decision Q4, catalog review |
| 2026-10-27 | §8 | Time is integer milliseconds (`Timestamp`, `Millis`), not `SystemTime`/`Duration`. Edge confidence is per-mille (`Confidence(u16)`), not `f32`. `Value` has no float variant. | Keeps the types inside the Verus subset, makes the fake clock exact, and gives the journal a stable encoding. |
| 2026-10-27 | §8 | Schema additions for the gaps in `docs/catalog-review.md` §3: `RejectReason::{Unauthorized, Interrupted, NoSpace}` (G1), `DerivedFacts::changes_desired` (G2), `SystemState::accepted_baseline` (G3), `UnitKind::Target` (G4), `DriverRef` (G6), `Evidence::probe` (G11, otherwise evidence can't be matched to its probe), `Transaction::prior_driver` (G12, §12 says the previous driver is "recorded at Prepared" but §8 has no field for it). Also `UnitStatus::NotExpected`: §8 says a unit whose condition doesn't hold "reports its observed status", but mapping that onto `Running` would break I4. `Transition::Resolve`: §12c calls `resolve` "a transition of its own". `RejectReason::{Refinement, ApprovalExpired}`: named reasons for §12 steps 3 and 5. | Owner accepted the suggested fixes, 2026-10-26. |
| 2026-10-27 | §8, §12 | Mutating backend calls take the journaled `OpId` instead of `&Lease`. The OpId carries `(txn, epoch)` for fencing and is the tag `jobs_tagged` looks up, so one argument does both jobs. `Lease` gains `txn`. `GenerationBackend` gains `boot_default`, `source_hash` (stale check), `override_hash` and `swap_override` (§9 step 4 promotion and restore), since the protocol needs each of these. | The §8 signatures could not express fencing by transaction, or the promotion step. |
| 2026-10-27 | §12 | Lease transfer is a compare-and-swap record in the journal (`Takeover { from_epoch, lease }`), validated under the journal's `flock`. `txn/<txn>/lease` holds only the fence epoch, written by atomic rename *before* the journal record, so a crash between the two leaves the old owner fenced. A takeover from an epoch the caller didn't observe backs off. | The journal is already the serialization point and the source of truth for the epoch. A second, separately locked lease file would add a split-brain case without adding protection. |
| 2026-10-27 | §18.1 | The demo script is `crates/gym/demo.sh`, not `gym/demo.sh`. | Follows the §6 layout, where `gym` lives under `crates/`. |
| 2026-10-27 | §18.9, §17a | `exec` was built before the `policy` proofs landed, which §18.9 forbids; the owner's instruction to build everything needed for user testing took precedence. The proofs landed the same day, after the owner approved building Verus. | Owner instruction 2026-10-27. |
| 2026-10-27 | §8, §17a | **Sets the proofs read are vectors.** vstd specifies `BTreeSet`/`BTreeMap` only for key types with an ordering spec, which `String` and our derived enums lack. The owner chose vectors with linear search over assuming one. So `Sensitivities` is five flags, `ConfigDiff::options` is a `PathMap` (a sorted `Vec`), `DerivedFacts::affected_units` is a sorted `Vec`, and `policy`'s `Settings`/`Tables` hold `Vec`s. JSON formats are unchanged. `PolicyVersion` hashes the tables with their name lists sorted. | Keeps the proofs free of a `String` ordering assumption. |
| 2026-10-27 | §11 (I11) | `decide` classifies this change's diff and the session's cumulative diff separately, instead of their composition. The result is identical when the cumulative diff has no entry that starts and ends at the same value (which `ConfigDiff::then` never produces) and stricter otherwise. `POLICY_REVISION` is `phase-a.2`. | The composition needs option-value equality, which the proofs keep opaque; an option the change returns to its start drops out of the composition but is in the change's own diff. |
| 2026-10-27 | §11 | `policy::Input` carries `known_good`, `live_tested` and the cumulative diff instead of the whole `SystemState` and `Session`. | `decide` reads nothing else from them, and the smaller input keeps the verified types small. |
| 2026-10-27 | §17 | Backends talk to the system through its command-line tools (`systemctl`, `loginctl`, `nix`, `nix-hash`, `systemd-run`, `nmcli`), not zbus. | Stable output formats, one uniform path for user managers (`--machine=<uid>@.host --user`), and a much smaller dependency set. zbus can replace `systemctl` behind the same trait later. |
| 2026-10-27 | §6 | The real backends are one crate (`crates/backends/linux`) with a module per backend (`systemd`, `logind`, `sysfs`, `nixos`, `probe`, `runtime`, `process`), not separate crates. The in-memory fake machine is `crates/fake` and does no I/O. There is also an `ipc` crate (the socket protocol the CLI and daemon share). | One wiring point for the daemon and the watchdog. The dependency rule still holds: `schema`, `policy`, `txn`, `exec`, `diagnose`, `incident` and `state` depend on no backend crate (the fake appears only as a dev-dependency). |
| 2026-10-27 | §8, §9 | Generation ids are Planarian's own (`/var/lib/planarian/generations.json`), mapping to system store paths, not system-profile numbers. | A candidate needs an id before it enters the profile at `publish_boot`. |
| 2026-10-27 | §8 | `ProbeKind` gains `FreeSpace { path, min_bytes, min_permille }` (§10 storage units) and `SessionTarget { target, within }` (§9 graphical-session: "target reached within 60 s of that session's creation", per session id). `Incident` gains `kind` (Repair or Diagnostic), `next_attempt` and `regressions`; `IncidentState::Escalated` gains `until`. `Transaction` gains `check: CheckContext` (candidate and base manifests and pre-state statuses), so the watchdog can run the probe check from the journal alone. | Each is needed to implement a §9/§10/§12/§13 rule as written, and to survive a restart. |
| 2026-10-27 | §12 | A `StopAndSuppress`'s suppression is journaled before its `Activating` record, not just before the stop call. | Found by the gym: a crash between Activating and the suppression lost the user's stop, while the transaction still read Committed. Now, once the stop is recorded at all, the repair loop leaves the unit alone. |
| 2026-10-27 | §12 | The daemon renews its leases from a separate thread (a `Renew` journal record every 20 s while a transaction it owns is mid-flight). | Otherwise, a live daemon blocked in a 15-minute activation would look abandoned to the watchdog once the deadline passed. |
| 2026-10-27 | §10, §16 | `known_good` moves only by boot confirmation: when the daemon starts on a boot of the live-tested generation and canonical probes pass at the 10-minute checkpoint, plus initial enrollment. A live commit sets `live_tested` only. | Conservative reading of I1. The cost is that until the next reboot, Rollback goes further back than the last good change. |
| 2026-10-27 | §13 | The diagnoser searches depth 1, not up to 2. A dependent's own incident supplies the second step (driver rebound, then pipewire restarted). It never proposes a Rollback over a generation Planarian didn't build (owner decision Q3), and never proposes runtime-option changes (so the catalog's Wi-Fi diagnoser case is unsupported). | Simpler, and enough for the Phase A families. Revisit with the held-out families in Phase B. |
| 2026-10-27 | §12b | Space budgets (generations ≤ 20% of the store's filesystem, snapshots ≤ 10%) and `BudgetUnsatisfiable` are **not implemented**. GC keeps the newest 10 profile generations (3 when emergency) plus the protected set, and never removes a protected generation from the boot menu. | Not needed for initial user testing. Follow-up. |
| 2026-10-27 | §16a | **The visual console (iced) is not built.** `planarian status` gives the same desired, observed and health information, plus incidents, pending approvals, the interlock and the reconciliation record. | Not needed for initial user testing, and a large dependency. Follow-up. |
| 2026-10-27 | §9 | "The manifest and the override file have `Sensitivity::{Security}`" is read as follows. A change that edits the manifest (`services.planarian.*`) is Security (`touches_manifest`, AskFirst). A catalog change that writes the override file is classified by the options it sets, so a font-scale change stays Tested. A hand edit of the override file is a third-party change: promotion stops with RecoveryFailed, and unit operations go on working. | Read literally, every catalog change would be AskFirst, and the §15 cases and the GA demo contradict that. |
| 2026-10-27 | §12a | Font scale and keyboard layout have no live mechanism in Phase A. `SetRuntimeOption` records that and the write-back (a Tested catalog change) applies the setting. Wi-Fi selection is live (`nmcli connection up`). Volume and brightness are not in the allowlist. | No session-independent way to change them live from a system daemon. |
| 2026-10-27 | §12 | Approvals parked when the daemon stops are not carried over. On restart the crash table marks those transactions `Rejected(Interrupted)`, and the user asks again. | The crash table's rule for Prepared, applied as written. |
| 2026-10-27 | §17 | Rust is pinned to 1.95.0 (what nixpkgs 26.05 ships), and nixpkgs is pinned through `git+https://github.com/NixOS/nixpkgs?ref=nixos-26.05` rather than `github:`. | The package must build with the platform's rustc. The `github:` fetcher goes through the GitHub API, which the build environment cannot reach. |
| 2026-10-27 | §15 | The gym's fake harness runs transactions synchronously. A fault timed to a journal state is armed through a hook in the fake machine (`edit_on_stage`, `nospace_on_build`, `block_on_activate`, `fail_publish`), and a daemon kill becomes a crash point on the transaction before it. Rejections that happen before a transaction exists are judged from the executor log. | Same semantics as the catalog's timed steps, without threads. |
| 2026-10-27 | §12, §17a | **Ledger representation for the `txn` proofs.** `Ledger::live` and `Ledger::interlock` are `IdMap`s (sorted vectors) instead of `BTreeMap`s, serialized as the same JSON objects. `apply` consumes its record. `LedgerError::IllegalStep` and `BadPrepared` carry `&'static str`. A checkpoint read from disk is rejected unless it satisfies the proved ledger invariant. `validate` also refuses a Prepared id of `u64::MAX` and a sequence past `u64::MAX` (arithmetic the proofs must bound). | As for `policy`: vstd specifies `BTreeMap` only for keys with an ordering spec. |
| 2026-10-27 | §12b | **Collection bounds, as read.** "Whichever bound is hit first collects oldest-first down to the other" is implemented as: when either bound (count, space) is exceeded, collect unprotected generations oldest first until both hold. Size is the combined closure of the kept generations (`nix path-info -r`), against the share of the filesystem holding `/nix/store`. `CollectGarbage { emergency: true }` (a nearly full store or journal filesystem) keeps at most 3. Snapshot budgets wait for the Phase C snapshot backend. | The literal sentence admits more than one reading; this one never keeps more than either bound allows. |
| 2026-10-27 | §12b, §8 | The daemon checks the bounds hourly and, if something can be collected, submits `CollectGarbage` itself with a new `Source::Maintenance` (not in §8's list). `BudgetUnsatisfiable` is a notice and a line in `planarian status` (the console's job in §16a), not an `Outcome`: the collection itself succeeded. | §12b implies automatic collection; attributing it to the user or the diagnoser would misreport who acted. |
