# Deviations

Where the implementation departs from `docs/SPEC.md`: SHOULD-level choices made differently (§5 preamble) and places where NixOS and the spec disagree on mechanism (§18.7). One entry per deviation.

| Date | Spec § | Deviation | Reason |
| --- | --- | --- | --- |
| 2026-10-26 | §15 | A catalog case whose VM fixture can't be made reliable (S3 suspend, mac80211_hwsim, greeter automation, withheld D-Bus replies) may run on `harness = ["fake"]` only. Each such move gets its own row here. | Owner decision Q4, catalog review |
| 2026-10-27 | §8 | Time is integer milliseconds (`Timestamp`, `Millis`), not `SystemTime`/`Duration`. Edge confidence is per-mille (`Confidence(u16)`), not `f32`. `Value` has no float variant. | Keeps the types inside the Verus subset, makes the fake clock exact, and gives the journal a stable encoding. |
| 2026-10-27 | §8 | Schema additions for the gaps in `docs/catalog-review.md` §3: `RejectReason::{Unauthorized, Interrupted, NoSpace}` (G1), `DerivedFacts::changes_desired` (G2), `SystemState::accepted_baseline` (G3), `UnitKind::Target` (G4), `DriverRef` (G6), `Evidence::probe` (G11, otherwise evidence can't be matched to its probe), `Transaction::prior_driver` (G12, §12 says the previous driver is "recorded at Prepared" but §8 has no field for it). Also `UnitStatus::NotExpected`: §8 says a unit whose condition doesn't hold "reports its observed status", but mapping that onto `Running` would break I4. `Transition::Resolve`: §12c calls `resolve` "a transition of its own". `RejectReason::{Refinement, ApprovalExpired}`: named reasons for §12 steps 3 and 5. | Owner accepted the suggested fixes, 2026-10-26. |
| 2026-10-27 | §8, §12 | Mutating backend calls take the journaled `OpId` instead of `&Lease`. The OpId carries `(txn, epoch)` for fencing and is the tag `jobs_tagged` looks up, so one argument does both jobs. `Lease` gains `txn`. `GenerationBackend` gains `boot_default`, `source_hash` (stale check), `override_hash` and `swap_override` (§9 step 4 promotion and restore), since the protocol needs each of these. | The §8 signatures could not express fencing by transaction, or the promotion step. |
| 2026-10-27 | §12 | Lease transfer is a compare-and-swap record in the journal (`Takeover { from_epoch, lease }`), validated under the journal's `flock`. `txn/<txn>/lease` holds only the fence epoch, written by atomic rename *before* the journal record, so a crash between the two leaves the old owner fenced. A takeover from an epoch the caller didn't observe backs off. | The journal is already the serialization point and the source of truth for the epoch. A second, separately locked lease file would add a split-brain case without adding protection. |
| 2026-10-27 | §18.1 | The demo script is `crates/gym/demo.sh`, not `gym/demo.sh`. | Follows the §6 layout, where `gym` lives under `crates/`. |
| 2026-10-27 | §18.9, §17a | `exec` was built before the `policy` proofs landed, which §18.9 forbids; the owner's instruction to build everything needed for user testing took precedence. The proofs landed the same day, after the owner approved building Verus. | Owner instruction 2026-10-27. |
| 2026-10-27 | §8, §17a | **Sets the proofs read are vectors.** vstd specifies `BTreeSet`/`BTreeMap` only for key types with an ordering spec, which `String` and our derived enums lack. The owner chose vectors with linear search over assuming one. So `Sensitivities` is five flags, `ConfigDiff::options` is a `PathMap` (a sorted `Vec`), `DerivedFacts::affected_units` is a sorted `Vec`, and `policy`'s `Settings`/`Tables` hold `Vec`s. JSON formats are unchanged. `PolicyVersion` hashes the tables with their name lists sorted. | Keeps the proofs free of a `String` ordering assumption. |
| 2026-10-27 | §11 (I11) | `decide` classifies this change's diff and the session's cumulative diff separately, instead of their composition. The result is identical when the cumulative diff has no entry that starts and ends at the same value (which `ConfigDiff::then` never produces) and stricter otherwise. `POLICY_REVISION` is `phase-a.2`. | The composition needs option-value equality, which the proofs keep opaque; an option the change returns to its start drops out of the composition but is in the change's own diff. |
| 2026-10-27 | §11 | `policy::Input` carries `known_good`, `live_tested` and the cumulative diff instead of the whole `SystemState` and `Session`. | `decide` reads nothing else from them, and the smaller input keeps the verified types small. |
| 2026-10-27 | §17 | Backends talk to the system through its command-line tools (`systemctl`, `loginctl`, `nix`, `nix-hash`, `systemd-run`, `nmcli`), not zbus. | Stable output formats, one uniform path for user managers (`--machine=<uid>@.host --user`), and a much smaller dependency set. zbus can replace `systemctl` behind the same trait later. |
| 2026-10-27 | §6 | The real backends are one crate (`crates/backends/linux`) with a module per backend (`systemd`, `logind`, `sysfs`, `nixos`, `probe`, `runtime`, `process`), not separate crates. The in-memory fake machine is `crates/fake` and does no I/O. There is also an `ipc` crate (the socket protocol the CLI and daemon share). | One wiring point for the daemon and the watchdog. The dependency rule still holds: `schema`, `policy`, `txn`, `exec`, `diagnose`, `incident` and `state` depend on no backend crate (the fake appears only as a dev-dependency). |
| 2026-10-27 | §8, §9 | Generation ids are Planarian's own (`/var/lib/planarian/generations.json`), mapping to system store paths, not system-profile numbers. | A candidate needs an id before it enters the profile at `publish_boot`. |
| 2026-10-27 | §8 | `ProbeKind` gains `FreeSpace { path, min_bytes, min_permille }` (§10 storage units) and `SessionTarget { target, within }` (§9 graphical-session: "target reached within 60 s of that session's creation", per session id). `Incident` gains `kind` (Repair or Diagnostic), `next_attempt` and `regressions`; `IncidentState::Escalated` gains `until`. `Transaction` gains `check: CheckContext` (candidate and base manifests and pre-state statuses), so the watchdog can run the probe check from the journal alone. | Each is needed to implement a §9/§10/§12/§13 rule as written, and to survive a restart. |
| 2026-10-27 | §12 | A `StopAndSuppress`'s suppression is journaled before its `Activating` record, not just before the stop call. | Found by the gym: a crash between Activating and the suppression lost the user's stop, while the transaction still read Committed. Now, once the stop is recorded at all, the repair loop leaves the unit alone. |
| 2026-10-27 | §12 | The daemon renews its leases from a separate thread (a `Renew` journal record every 20 s while a transaction it owns is mid-flight). | Otherwise, a live daemon blocked in a 15-minute activation would look abandoned to the watchdog once the deadline passed. |
| 2026-10-27 | §10, §16 | `known_good` moves only by boot confirmation: when the daemon starts on a boot of the live-tested generation and canonical probes pass at the 10-minute checkpoint, plus initial enrollment. A live commit sets `live_tested` only. | Conservative reading of I1. The cost is that until the next reboot, Rollback goes further back than the last good change. |
| 2026-10-27 | §13 | The diagnoser searches depth 1, not up to 2. A dependent's own incident supplies the second step (driver rebound, then pipewire restarted). It never proposes a Rollback over a generation Planarian didn't build (owner decision Q3), and never proposes runtime-option changes (so the catalog's Wi-Fi diagnoser case is unsupported). | Simpler, and enough for the Phase A families. Revisit with the held-out families in Phase B. |
| 2026-10-27 | §9 | "The manifest and the override file have `Sensitivity::{Security}`" is read as follows. A change that edits the manifest (`services.planarian.*`) is Security (`touches_manifest`, AskFirst). A catalog change that writes the override file is classified by the options it sets, so a font-scale change stays Tested. A hand edit of the override file is a third-party change: promotion stops with RecoveryFailed, and unit operations go on working. | Read literally, every catalog change would be AskFirst, and the §15 cases and the GA demo contradict that. |
| 2026-10-27 | §12a | Font scale and keyboard layout have no live mechanism in Phase A. `SetRuntimeOption` records that and the write-back (a Tested catalog change) applies the setting. Wi-Fi selection is live (`nmcli connection up`). Volume and brightness are not in the allowlist. | No session-independent way to change them live from a system daemon. |
| 2026-10-27 | §12 | Approvals parked when the daemon stops are not carried over. On restart the crash table marks those transactions `Rejected(Interrupted)`, and the user asks again. | The crash table's rule for Prepared, applied as written. |
| 2026-10-27 | §17 | Rust is pinned to 1.95.0 (what nixpkgs 26.05 ships), and nixpkgs is pinned through `git+https://github.com/NixOS/nixpkgs?ref=nixos-26.05` rather than `github:`. | The package must build with the platform's rustc. The `github:` fetcher goes through the GitHub API, which the build environment cannot reach. |
| 2026-10-27 | §15 | The gym's fake harness runs transactions synchronously. A fault timed to a journal state is armed through a hook in the fake machine (`edit_on_stage`, `nospace_on_build`, `block_on_activate`, `fail_publish`), and a daemon kill becomes a crash point on the transaction before it. Rejections that happen before a transaction exists are judged from the executor log. | Same semantics as the catalog's timed steps, without threads. |
| 2026-10-27 | §12, §17a | **Ledger representation for the `txn` proofs.** `Ledger::live` and `Ledger::interlock` are `IdMap`s (sorted vectors) instead of `BTreeMap`s, serialized as the same JSON objects. `apply` consumes its record. `LedgerError::IllegalStep` and `BadPrepared` carry `&'static str`. A checkpoint read from disk is rejected unless it satisfies the proved ledger invariant. `validate` also refuses a Prepared id of `u64::MAX` and a sequence past `u64::MAX` (arithmetic the proofs must bound). | As for `policy`: vstd specifies `BTreeMap` only for keys with an ordering spec. |
| 2026-10-27 | §12b | **Collection bounds, as read.** "Whichever bound is hit first collects oldest-first down to the other" is implemented as: when either bound (count, space) is exceeded, collect unprotected generations oldest first until both hold. Size is the combined closure of the kept generations (`nix path-info -r`), against the share of the filesystem holding `/nix/store`. `CollectGarbage { emergency: true }` (a nearly full store or journal filesystem) keeps at most 3. Snapshot budgets wait for the Phase C snapshot backend. | The literal sentence admits more than one reading; this one never keeps more than either bound allows. |
| 2026-10-27 | §12b, §8 | The daemon checks the bounds hourly and, if something can be collected, submits `CollectGarbage` itself with a new `Source::Maintenance` (not in §8's list). `BudgetUnsatisfiable` is a notice and a line in `planarian status` (the console's job in §16a), not an `Outcome`: the collection itself succeeded. | §12b implies automatic collection; attributing it to the user or the diagnoser would misreport who acted. |
| 2026-10-27 | §12, principle 9 | **A user's stop survives Planarian's own activations.** `switch-to-configuration` restarts every active target, which starts the services they want, including one a user stopped on purpose. A suppression from `StopAndSuppress` now records `stopped: true`, and after activating a candidate (before Checking) and after activating the revert target, the kernel stops those units again through the journaled `stop` op. Suppressions written before this change read as `stopped: false`. | The spec covers the repair loop ("a user stops a running service: stays stopped") but not activations; found by running the console against the fake machine. |
| 2026-10-27 | §16a | **Console.** The daemon answers a new `Request::Console` with everything the console shows. "Minimized unless … the last boot reverted" uses "the most recent generation change was reverted", which the journal records. The console is its own package, and `services.planarian.console.enable` (off by default, on in the reference module) starts it with the graphical session. It has no §11 disruption notice with a 10-second cancel window: under the §11 floors every daemon-initiated transition with disruption ≥ SessionLoss is AskFirst (the daemon is never a user), so the window could only follow an approval a person just gave. | The console cannot see boot-time reverts directly, and the journal records the last change's outcome. A server should not carry GUI libraries. |
| 2026-10-27 | §17a | **`schema::digest` has no Verus proof.** Proving it needs `SystemState.units` as a vector-backed map (about 46 call sites in 22 files) plus trusted, deterministic encoding, hashing and sorting, and what would remain is "the projection drops timestamps and resources". It is checked instead by a property test over random states (timestamps and resources never change the digest; anything the state says does), which fails if `observed_at` is mixed in. | Cost against content; the owner may ask for the refactor. |
| 2026-10-27 | §11, §16a | **Long phases run beside the daemon's core.** A catalog change's stage, evaluate and build (§9 steps 1–3, before anything is journaled) run on a worker thread with a clone of the generations backend; the core keeps observing, repairing and answering, and `status` says "building … (N min so far); repairs go on meanwhile". When the build finishes, the core plans and runs the change against a fresh observation, using the prebuilt candidate only if the live override file is the one it was built from (otherwise it builds again). One build at a time; later changes queue. The mutating phases (activate, check, publish, promote, revert) still run on the core: I6 forbids any other transition then anyway, and `status`, `log` and the console are answered meanwhile from a snapshot marked "busy with …". | Found by running the demo VM: `planarian status` and the console hung for the length of a build, and so did repairs. |
| 2026-10-27 | §13 | **Startup grace (an addition).** A unit whose process is up but whose Readiness probe fails is not divergent for `startupGrace` seconds after it came up (default 90; per unit `units.<name>.startupGrace`; the demo VM uses 180). "Came up" is when Planarian first sees it running after boot or a daemon restart, when it turns from down to up, or when a `RestartUnit` transaction finishes. Within the grace no incident opens and an open one is not actionable. A crash (`Failed`) gets no grace. | Found under emulation: a slow boot made gym-web fail its probe while still starting, and the restarts used up its budget before anything was wrong. |
| 2026-10-27 | §15, §17 | **The VM harness's fault injection lives in the real binaries, behind a cargo feature.** `gym-hooks` (off in the shipped package; on in `nix/package.nix { gymHooks = true; }`) lets the daemon take a crash point from `/run/planarian-gym/crash` and abort as SIGKILL would, and the backends take results, delays or withheld replies from `/run/planarian-gym/hooks.json`. The socket protocol gains `GymPropose` (submit a transition as a proposal, optionally with a stale digest or narrowed `may_change`) and `GymCompact`; a daemon without the feature answers them with an error. Torn writes stay unsupported in the VM (they need to interrupt the daemon's own write). | The catalog's crash and backend-fault cases need the real daemon to fail at exact points; timing kills from outside cannot hit brief states. |
| 2026-10-27 | §12c | **The installer offers ext4 and btrfs, not ZFS.** On btrfs it sets `chattr +C` on `/var/lib/planarian` before the journal exists. The ZFS dataset reservation is not implemented. It is also the live image rather than a separate one. | ZFS on root needs its own pool layout, boot setup and host ID, which is a separate installer path. One image means you can try the demo before you install. |
| 2026-10-28 | §8, §12a, §13 | **Runtime repair (an addition).** `UnitDef` gains `runtime_repair`: a runtime-settable option whose other values can restore the unit (`wifi.network`, set with `services.planarian.units.<name>.runtimeRepair`). `RuntimeOptionBackend` gains `alternatives` (for Wi-Fi: known networks in range besides the current one), and the diagnoser proposes `SetRuntimeOption` to one of them, before a restart, at Runtime tier; the §11 floors make it AskFirst. Wi-Fi health is a readiness probe on NetworkManager, not on the radio device: per §8 a bound device's status does not read its probes. The reference configuration does not declare it (a machine without Wi-Fi would always look Degraded). | §15 requires the daemon to propose a runtime Wi-Fi change, and nothing in §8 or §13 could express which units an option repairs. |
| 2026-10-29 | §10, §15 | `net-gateway-down` (traffic to the gateway dropped) expects no incident: every probe on the way times out, and a timeout is Unknown, never Failed. Planarian re-observes (a Diagnostic incident, no repair budget), restarts nothing, and after 2 minutes says it can't reach the external dependency (`ExternalDependencyUnreachable`), then that it answers again. The §10 gym case "the external dependency is down" is `net-upstream-down`: the upstream service stopped, connections refused, an incident on the external unit, named as the client's root cause. The fake harness models dropped traffic as timeouts (it modelled it as refused, which is how the catalog came to expect an incident). | Owner decision 2026-10-29: keep the §10 rule rather than treat sustained timeouts as down. |
| 2026-10-29 | §15 | `suspend-resume` runs on `harness = ["fake"]` only (owner decision Q4's rule). QEMU never woke the test VM: not from S3 (`system_wakeup`), not from suspend-to-idle with an RTC alarm and the RTC enabled as a wakeup source. The fake models a suspend as time passing with nothing running, the daemon included. | Owner decision Q4 (2026-10-26) |
| 2026-10-29 | §11 | **The unattributed residue is decided by what systemd reports, not by who sent the signal**, which is not observable. Residue (an inferred override under Relaxed and Standard): a non-Security unit stopped by `SIGKILL`, `SIGTERM`, `SIGINT` or `SIGHUP` with `Result=signal`, or by a `systemctl stop` that Planarian did not issue, and still stopped after systemd's own restart policy. Fault: a crash signal, a non-zero exit, `Result=oom-kill`, a failed start, a timeout. A device found unbound is always a fault. §12f's "PipeWire kill" reads as a crash. | Owner decision Q5, catalog review §8. |
| 2026-10-29 | §8, §11 | **v4.4 schema, as implemented.** `Capabilities` is a set of flags (like `Sensitivities`) so the proofs can read it; it serializes as the list of members. `DerivedFacts` gains `affected_sessions` (sorted logind session ids the disruption lands on): §11's "own session" floor is per session and needs to know which, and an empty list never counts as own. `Actor::principal()` maps a user to `PrincipalId(uid)` and the daemon, watchdog, model and unattributed actor to fixed ids above every uid. Phase A grants: every user holds `OwnScope` and `UserControllable`; root and `planarian-admin` members also hold `Administrator` and `Approve`; root always does, so I17 holds. A `SetOverride` with `Absent` or `Detected` is refused before any mutation in Phase A (masking and detaching come later). The caller's logind session is read from `/proc/<pid>/cgroup` (`session-<id>.scope`), which is what `sd_pid_get_session` does. `SessionInfo` gains `active` (logind `State=active`). | Needed to implement §8 and §11 as written within the Verus subset. |
| 2026-10-29 | §11 (I19) | Approval stays root at an interactive terminal in Phase A (§16), and now also passes `may_approve`: the approver is never the proposer and holds the decision's class. So root cannot approve a change root proposed; a `planarian-admin` member proposes and root approves. On a one-person machine the same human is two principals (their uid and root); I19 holds per principal, not per person. | §16 and I19 together. |
| 2026-10-29 | §12c (I18) | **The hash chain has no key.** Each record carries the previous chain head and the checkpoint carries the head at its seq, so damage and naive edits are detected on read (at startup, by `planarian-recovery`'s independent check, and hourly by the running daemon), and nothing is truncated after a damaged record that later records follow. An edit to the very last record, or a root attacker who rewrites every later record and the checkpoint consistently, is not detected until the head is anchored outside the disk (measured boot, Phase E). Journal format 2; a format-1 journal is refused with instructions rather than truncated. | No secret is available to the core in Phase A. |
| 2026-10-29 | §12e, §12d | **Security floor in Phase A.** Derived at commit from the system packages' nixpkgs `meta.knownVulnerabilities` (`environment.systemPackages` only; packages pulled in by services are not inspected), or set with `planarian mark-security-floor` on a generation that committed live; it only moves forward. A diagnoser Rollback whose target is below the floor is not proposed; the incident escalates with `RevertBlockedByFloor`. Boot entries below the floor are not yet *labeled* in the menu: the NixOS systemd-boot builder writes the titles, and changing them is left for the boot-chain work of Phase C. I16's bootloader half is held by construction and checked by test: Planarian sets the boot default only to a generation it committed, which is at or above the floor once it moves. | Labeling needs a bootloader hook Phase A does not own. |
| 2026-10-29 | §11 | **The residue under Guarded and Sealed.** Phase A ships only Standard (§12d); under Guarded or Sealed (settable for testing) an unattributed stop is not inferred and is repaired as a fault, without the 10 s ask window, which comes with the other postures in Phase C. The inference needs a transition Planarian saw (running at the last tick, down now) that none of its own transactions caused, and applies only to units systemd will not restart; units stopped with the inferred one (their `Requires=`) are linked to it and released with it. | Phase A ships Standard. |
| 2026-10-29 | §9, §10 | **Per-session desktop readiness and foreground signals.** The graphical-session unit is one instance per established session (`target@<uid>/<session>:graphical-session`), judged by a compositor process in that session's cgroup when `services.planarian.sessionCompositors` names one, else by the user's graphical-session.target (corroboration only, so a second session of one uid is told apart only with the list set). The list is empty by default until checked on the reference desktop, and `session-second-compositor-fails` runs on the fake only (the gym VM's compositor fixture is a user service). Foreground (§10) comes from a Feral GameMode client on the user's bus or a gamescope in the session; the idle-inhibitor and Do Not Disturb signals have no session-independent source yet. | Q4-style: no reliable VM fixture yet. |
| 2026-10-29 | §12d, §10 | **Failure posture, Phase A.** `nix/posture.nix` implements the Standard posture in systemd and shell. Absent comes from an independent check of `planarian-ready.target` against the boot-ready timeout, and from `planariad` being stopped outside a shutdown. Crashed comes from `OnFailure=` once the restart budget (5 in 300 s) is spent. Integrity comes from status 78 of `planariad` (broken journal chain, a boot-report finding) or `planarian-recovery` (core hash ≠ the hash recorded at build: I2 without a signature, which comes in E). The responses: an alarm in `/run/planarian/alarm`, on the login screen (`/run/issue.d`) and by `wall`; administrators notified in the journal at alert level (no remote channel in A); agent units conflicted off (I20); sshd restricted to administrators, or closed for Integrity. The boot report checks units only (an active unit whose file is outside the store and not a generator's), not processes. The administrator's exit is `sudo planarian-ack` (no `planarian ack` daemon verb: it must work while the daemon is down). | §12d asks for exactly this split; the parts left out need hardware or later phases. |
